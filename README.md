### 🧩 Terraform Reusable Module Architecture (Parent → Child Pattern)

> I design and maintain a **modular Terraform library** following the Hub-Spoke model with strict parent-child module separation — enabling teams to provision compliant, production-ready Azure Landing Zones with minimal configuration.

```hcl
# ─────────────────────────────────────────────
# ROOT MODULE (Parent) — calls all child modules
# ─────────────────────────────────────────────
module "networking" {
  source              = "./modules/networking"
  vnet_name           = var.vnet_name
  address_space       = var.address_space
  resource_group_name = module.resource_group.name
}

module "compute" {
  source              = "./modules/compute"
  vm_name             = var.vm_name
  subnet_id           = module.networking.subnet_id
  key_vault_id        = module.security.key_vault_id
}

module "security" {
  source              = "./modules/security"
  environment         = var.environment
  tenant_id           = var.tenant_id
}

module "monitoring" {
  source              = "./modules/monitoring"
  log_analytics_ws_id = module.security.log_analytics_id
}
```

#### Terraform Best Practices I Follow

```
✅  Remote State in Azure Blob with State Locking via Azure Table Storage
✅  Separate tfvars per environment (dev / staging / prod)
✅  Dynamic blocks & locals for DRY code
✅  Terraform workspaces aligned with Azure subscriptions
✅  Sentinel policies for compliance guardrails
✅  Pre-commit hooks: terraform fmt, validate, tfsec, tflint
✅  Module versioning via Git tags & Terraform Registry
✅  Outputs chained across modules — no hardcoded resource IDs
```

> I engineer **best-practice YAML pipelines** with separation of concerns — a single pipeline handles `init → validate → plan`, then a **manual approval gate via PR** triggers the isolated `apply` pipeline.

### 📄 Sample YAML Pipeline — IaC Validation (Pipeline 1)

```yaml
# ─────────────────────────────────────────────────────
# azure-pipelines-validate.yml
# Pipeline 1: Init → Validate → Plan (No Apply Here!)
# ─────────────────────────────────────────────────────
trigger:
  branches:
    include:
      - feature/*
      - fix/*

pr:
  branches:
    include:
      - main

pool:
  vmImage: ubuntu-latest

variables:
  - group: terraform-global-vars
  - name: TF_VERSION
    value: '1.7.0'
  - name: WORKING_DIR
    value: '$(System.DefaultWorkingDirectory)/infrastructure'

stages:
  - stage: Validate
    displayName: '🔍 Terraform Validate & Plan'
    jobs:
      - job: TerraformValidate
        displayName: 'Init, Lint, Validate, Plan'
        steps:
          - task: TerraformInstaller@1
            displayName: '📦 Install Terraform'
            inputs:
              terraformVersion: $(TF_VERSION)

          - task: TerraformTaskV4@4
            displayName: '⚙️ Terraform Init'
            inputs:
              provider: azurerm
              command: init
              workingDirectory: $(WORKING_DIR)
              backendServiceArm: $(ARM_SERVICE_CONNECTION)
              backendAzureRmResourceGroupName: $(TF_BACKEND_RG)
              backendAzureRmStorageAccountName: $(TF_BACKEND_SA)
              backendAzureRmContainerName: tfstate
              backendAzureRmKey: '$(Environment).terraform.tfstate'

          - script: |
              tflint --init
              tflint --format compact
            displayName: '🧹 TFLint — Linting Check'
            workingDirectory: $(WORKING_DIR)

          - task: TerraformTaskV4@4
            displayName: '✅ Terraform Validate'
            inputs:
              provider: azurerm
              command: validate
              workingDirectory: $(WORKING_DIR)

          - task: TerraformTaskV4@4
            displayName: '📋 Terraform Plan'
            inputs:
              provider: azurerm
              command: plan
              workingDirectory: $(WORKING_DIR)
              environmentServiceNameAzureRM: $(ARM_SERVICE_CONNECTION)
              commandOptions: '-out=$(Build.ArtifactStagingDirectory)/tfplan -var-file=envs/$(Environment).tfvars'

          - task: PublishPipelineArtifact@1
            displayName: '📤 Publish Plan Artifact'
            inputs:
              targetPath: $(Build.ArtifactStagingDirectory)/tfplan
              artifact: terraform-plan
              publishLocation: pipeline
```

### 📄 Sample YAML Pipeline — Apply with Manual Approval (Pipeline 2)

```yaml
# ─────────────────────────────────────────────────────
# azure-pipelines-apply.yml
# Pipeline 2: Manual Approval Gate → Apply
# Triggered ONLY after PR merge to main (trunk)
# ─────────────────────────────────────────────────────
trigger:
  branches:
    include:
      - main

pool:
  vmImage: ubuntu-latest

variables:
  - group: terraform-global-vars
  - name: TF_VERSION
    value: '1.7.0'
  - name: WORKING_DIR
    value: '$(System.DefaultWorkingDirectory)/infrastructure'

stages:
  - stage: ApprovalGate
    displayName: '⏸️ Manual Approval Gate'
    jobs:
      - job: WaitForApproval
        displayName: 'Awaiting Senior Engineer Approval'
        pool: server
        timeoutInMinutes: 1440   # 24-hour window
        steps:
          - task: ManualValidation@0
            displayName: '🔐 Manual Sign-off Required'
            inputs:
              notifyUsers: |
                senior-devops@company.com
              instructions: |
                ⚠️ Terraform Apply is pending your approval.
                Review the plan artifact before proceeding.
                Check: Cost estimate, compliance policies, resource changes.
              onTimeout: reject

  - stage: Deploy
    displayName: '🚀 Terraform Apply'
    dependsOn: ApprovalGate
    condition: succeeded('ApprovalGate')
    jobs:
      - deployment: TerraformApply
        displayName: 'Apply Infrastructure Changes'
        environment: $(Environment)
        strategy:
          runOnce:
            deploy:
              steps:
                - task: DownloadPipelineArtifact@2
                  displayName: '📥 Download Plan Artifact'
                  inputs:
                    artifact: terraform-plan
                    path: $(Pipeline.Workspace)/tfplan

                - task: TerraformInstaller@1
                  inputs:
                    terraformVersion: $(TF_VERSION)

                - task: TerraformTaskV4@4
                  displayName: '⚙️ Terraform Init (Apply Stage)'
                  inputs:
                    provider: azurerm
                    command: init
                    workingDirectory: $(WORKING_DIR)
                    backendServiceArm: $(ARM_SERVICE_CONNECTION)
                    backendAzureRmResourceGroupName: $(TF_BACKEND_RG)
                    backendAzureRmStorageAccountName: $(TF_BACKEND_SA)
                    backendAzureRmContainerName: tfstate
                    backendAzureRmKey: '$(Environment).terraform.tfstate'

                - task: TerraformTaskV4@4
                  displayName: '✅ Terraform Apply'
                  inputs:
                    provider: azurerm
                    command: apply
                    workingDirectory: $(WORKING_DIR)
                    environmentServiceNameAzureRM: $(ARM_SERVICE_CONNECTION)
                    commandOptions: '$(Pipeline.Workspace)/tfplan/tfplan'
```

## 🔀 Trunk-Based Development — My Branching Philosophy

<div align="center">

```
  main (TRUNK)  ════════════════════════════════════════════════════► 
                 │          │               │              │
                 │          │               │              │
              feature/    fix/           feature/      release/
              add-vnet   bug-123        aks-module     v2.1.0
                 │          │               │
              (short-lived branches — merged back within 24-48 hrs)
```

</div>

### Ground Rules I Follow for Trunk-Based Development

```
📌  All branches are short-lived (< 2 days ideally)
📌  Feature flags used for incomplete features in trunk
📌  PRs require: 1 reviewer + AI Copilot review + all CI checks green
📌  Commit messages follow Conventional Commits standard
📌  No long-running environment branches (dev/staging/prod managed via tfvars)
📌  Tags drive releases: vMAJOR.MINOR.PATCH (SemVer)
📌  Branch protection rules on main: no direct pushes, squash merges
📌  Release branches created from tags — never committed to directly
```
